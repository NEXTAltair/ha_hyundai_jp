# Documentation Maintenance Rules

ドキュメントが陳腐化する速度を、更新頻度の異なる情報を1つのファイルに混ぜないことで抑える方針。

> **プロジェクト固有:** 指針層ファイルの実際のパス (`CLAUDE.md` / `AGENTS.md` 等)、詳細層ドキュメントの一覧、レビュー周期は導入先で追記する。

## 核心ルール

**更新頻度で文書を層に分ける。** 年単位でしか変わらない原則と、機能追加のたびに変わる詳細を同じファイルに書くと、後者の変化に耐えられず前者ごと陳腐化する。
**機械で守れるものは機械に守らせる。** メタデータ・索引のように一貫性を人手のレビューだけに頼ると必ずドリフトする箇所は、単一の情報源 (frontmatter 等) から生成物として作り、生成物側の手編集を禁止する。
**参照されるほど正確さは失われやすい。** 具体パス・具体コマンド・具体的な件数のような「変わりやすい事実」への言及箇所を減らすほど、ドキュメント全体の正確性は保ちやすくなる。

## 3層ドキュメントアーキテクチャ

| 層 | 内容 | 更新頻度 | 例 |
|----|------|---------|----|
| 指針層 | AI エージェント / 開発者が最初に読む原則とワークフローへのポインタ | 四半期〜年単位 | `CLAUDE.md` 等のトップレベル指示ファイル |
| 詳細層 | 機能ごとの技術仕様、サービス一覧、テスト戦略などの具体的なドキュメント | 機能完成時 | `docs/*.md` |
| 実装層 | 実際に実行されるコード | リアルタイム (コード変更と同時) | ソースコードそのもの |

指針層は詳細層への**ポインタのみ**を持ち、詳細な仕様や変わりやすい事実 (ファイルパス一覧・件数・
コマンド例) を自身に書き込まない。詳細な内容は詳細層に置き、指針層からリンクする。これにより、
指針層は詳細層の変更頻度に引きずられず、レビュー頻度を低く保てる。

判断に迷ったら「この情報は年単位で安定しているか、機能追加のたびに変わるか」を基準に層を選ぶ。
安定した原則は指針層、具体的な実装詳細は詳細層、常に正しいのはコードだけ (実装層) という前提に立つ。

## 機械で守れるものは生成物にする

索引・目次・メタデータの一覧のように、「複数ファイルの内容を集約しただけ」の情報は、
ソースとなるメタデータ (frontmatter 等) を単一の情報源 (SSoT) とし、索引ファイル自体は
生成スクリプトの出力物として扱う。索引ファイルへの手編集は禁止し、レビューでは
「メタデータが正しいか」だけを確認する。これにより、索引の drift (メタデータと索引の不一致) が
構造的に起こらなくなる。

具体的な運用パターン (frontmatter 管理・索引再生成) は `okf-bundle` skill を参照。

## エージェントが読む開発ドキュメントは OKF バンドルとして記録する

詳細層のうち、**エージェントが後で読む前提の開発中ドキュメント** (設計書、仕様、実装計画、調査メモ、
検証記録、手順書、教訓、ADR、用語集など) は、種類を問わず frontmatter 付きの Markdown として
ドキュメントルート配下に置き、索引を生成物として保つ。

- frontmatter の `type` は必須。`title` / `description` / `timestamp` / `status` は推奨。
- 状態 (draft / active / superseded 等) や日付のようなスカラー値は frontmatter に置き、本文の散文に書かない。
- 新規作成時は本文より先に frontmatter を書く。frontmatter の無い開発ドキュメントを新たに増やさない。
- 既存の frontmatter 無し文書は段階的に付与する (検証は `--skip-missing` で未付与を除外できる)。
- 索引 (`index.md`) は生成物。文書を追加・編集したら再生成し、手で編集しない。

対象外は README (人間向け入口)、指針層 (`CLAUDE.md` / `AGENTS.md`)、生成物、コードコメント。
手順と検証スクリプトは `okf-bundle` skill を参照。

## ドキュメントの正確性は「参照が減るほど保たれる」

ドキュメントの陳腐化は、変わりやすい事実 (具体パス・具体コマンド・件数・Issue 番号など) への
言及が増えるほど進行が早くなる。同じ事実を複数箇所に書くと、変更のたびに全箇所を追従させる
負担が生じ、いずれか一箇所が更新漏れになる。

- 同じ事実は1箇所にしか書かない。他の場所からはその1箇所へのポインタで参照する。
- 汎用原則を記述する文書 (本 kit の `rules/*.md` など) には、具体パス・具体コマンド・具体的な
  Issue/PR 番号を書き込まない。導入先固有の値は導入先の記録に置き、原則側からは
  「導入先で追記する」という形でポイントする。
- 更新頻度が異なる情報を1つのセクションに混在させない (指針層に詳細層の内容を書き込まない)。

## 判断フロー

1. この情報は年単位で安定しているか? → YES → 指針層 (ポインタのみ)
2. 機能追加・変更のたびに変わる具体的な仕様か? → YES → 詳細層
3. 常に最新なのはコード自体か? → YES → 実装層 (ドキュメント化しない、コードコメントに留める)
4. 複数ファイルの内容を集約しただけの索引/メタデータ一覧か? → YES → frontmatter を SSoT にし、索引は生成物にする
5. 同じ事実を複数箇所に書きたくなったら? → 1箇所に集約し、他はポインタにする
