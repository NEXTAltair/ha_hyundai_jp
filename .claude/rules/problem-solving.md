# Problem Solving Rules

問題解決と設計判断の姿勢に関するルール。新機能の設計、バグ対応、ツール選定、共通処理の追加など、
「どう解くか」を決めるすべての場面に適用する。言語・スタック非依存。

> **プロジェクト固有:** 採用済みライブラリの一覧、選定基準の重み (ライセンス制約、社内標準 等)、
> 調査結果の記録先 (ADR / lessons-learned) のパスは導入先で追記する。

## 核心ルール

1. **過剰設計をしない**: 今ある問題を解く最小の変更にとどめる (YAGNI)。作業中に見つけた無関係なバグや
   改善点は直さず、成果報告の follow-up として挙げる。
2. **車輪の再発明をしない**: ユーティリティ、パーサ、リトライ、キャッシュ、CLI 引数処理などの「よくある処理」を
   自前で書く前に、標準ライブラリ → 既存依存 → プロジェクト内の既存コード → 実績あるサードパーティの順で探す。
3. **先行事例を先に調べる**: バグ・エラー・設計上の悩みは、自分で解法を考え始める前に web で丁寧に探す。
   公式ドキュメント、該当ライブラリの issue / changelog、同種の問題を扱った記事や実装を確認し、
   すでに知られている原因や定石があればそれに従う。

## 調査の手順

問題に着手したら、実装や修正案を書く前に次を行う:

1. **問題を一文にする**: 何が起きて何が期待と違うか。エラーメッセージや条件をそのまま検索語にできる形にする。
2. **既存物を探す**: 標準ライブラリ、`pyproject.toml` 等に既に入っている依存、プロジェクト内の類似コードを grep する。
   規模が大きい場合は `check-existing` skill (導入していれば) の手順に従う。
3. **web で先行事例を探す**: 公式ドキュメント (ライブラリ固有の話は Context7 等のドキュメント取得手段を優先)、
   GitHub issue / discussion、changelog、Stack Overflow 等を確認する。エラー文をそのまま検索し、
   バージョン差による既知の挙動変更がないかを見る。
4. **選択肢を並べて比較する**: 「既存ライブラリを使う / 既存コードを少し拡張する / 自前で書く」を比較し、
   自前実装を選ぶ場合はその理由 (既存物が要件を満たさない点) を明示する。
5. **根拠を残す**: 採用した先行事例・ドキュメントの URL と、検証した内容を成果報告や PR 説明に書く。
   検証していない前提は [unknowns-discovery.md](unknowns-discovery.md) の分類で残す。

## 検証は最小単位から

修正のたびにテストスイート全体を回さない。検証のコストも設計対象として扱う。

1. **変更に直接対応するテストだけを先に回す**: 触ったモジュールのテストファイル、または `-k` で該当ケースに絞る。
   失敗の再現と修正の確認はこの粒度で繰り返す。
2. **必要ならテストを 1 本足してから直す**: 再現テストが無い問題は、まず失敗するテストを書き、それが通ることを修正の完了条件にする。
3. **全体実行は最後に一度**: 局所テストが通ってから、CI と同じ filter で全体を一度だけ回す
   ([testing.md](testing.md) の「CI-equivalent filter」参照)。全体実行を試行錯誤の手段にしない。
4. **全体実行が長い場合はバックグラウンドで**: 待つ間に別の作業を進め、結果は通知で受け取る (待機方法は [testing.md](testing.md) 参照)。

## ライブラリ・ツール選定の基準

- **保守状況**: 最終リリース日、issue への反応、主要スタックの最新版への追従
- **適合度**: 要件の大半を素で満たすか。薄い wrapper で済む範囲か
- **ライセンス**: プロジェクトの配布形態と両立するか
- **依存の重さ**: 引き込む推移的依存の量、ビルド要件 (ネイティブ拡張等)
- **既存依存との重複**: 同じ役割のライブラリが既に入っていないか

これらを満たす候補があるなら、機能が一部足りなくても、まず採用して薄く補う案を検討する。
